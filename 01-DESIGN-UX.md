# 01 — Design & UX Rules

> Source: user-collected design notes and transcripts, organized without silently converting uncertain phrases into requirements.

## How to apply

- **Avoid by default unless explicitly requested:** recurring generic AI-generated design clichés and inaccessible or misleading UI.
- **Employ / consider where relevant:** UX laws and useful components. These are not orders to put every widget on every screen.
- **Do not confuse** a visual style reference with an automatic choice. The separate [Design Style Library](04-DESIGN-STYLE-LIBRARY.md) lists possibilities only.
- **Desktop is not the whole website.** Validate mobile layouts and touch/keyboard interactions.

## Expanded 45-law English study reference

See **[07 — 45 UX Laws, Effects & Design Heuristics](07-45-UX-LAWS-ENGLISH.md)** for the full **45-entry** researched index, its Hindi-to-English Instagram clip transcription, per-entry design checks, original-source citations, and uncertainty notes.

- The **30 entries from Laws of UX** plus **15 documented HCI / Gestalt / usability additions** make a curated teaching set, **not** a verified reproduction of the Instagram creator’s complete 45-episode sequence.
- Additional concepts to **consider when relevant**: Weber's Law, Steering Law, Power Law of Practice, Zeigarnik Effect, Choice Overload, Chunking, Cognitive Load, Cognitive Bias, Flow, Mental Models, Paradox of the Active User, Pareto Principle, Parkinson's Law, Selective Attention, Working Memory, Law of Uniform Connectedness, Law of Closure, Law of Continuity, Figure–Ground Principle, Law of Symmetry and Order, Law of Common Fate, Visibility of System Status, Error Prevention, User Control and Freedom, Consistency and Standards, and Match Between System and Real World.
- Existing principles **Recognition over Recall** and **Progressive Disclosure** are covered in the expanded reference too; avoid duplicating contradictory definitions.
- **The Aesthetic–Usability Effect does not mean a beautiful app actually works.** Continue to test functionality, accessibility, responsive behavior and honest product claims.
- From the source clips, **Day 5 is unresolved**, and **“Weber’s Illusion” was spoken, not conclusively “Weber’s Law.”** Do not silently replace one with the other.
- These guidelines **never override the avoid-by-default design rules** or authorize manipulative progress cues or unnecessary ornamentation.

## More practical patterns from the October 25 reel collection

The detailed explanations are in [13 — Design Interactions & Icon Styles](13-DESIGN-INTERACTIONS-ICON-STYLES.md), with original clip tracking in [16 — Reel Source Register](16-INSTAGRAM-REELS-SOURCE-REGISTER.md).

**Consider where relevant:** one dominant focal element with quieter supporting information; assigning meaning to accent colors (the **60–30–10** rule is an optional heuristic, not a compulsory ratio); submenu pointer-intent corridors to prevent accidental hover switching **with keyboard/touch equivalents**; confirmation dialogs that describe the consequence and use explicit action verbs.

**Avoid by default:** a modal that only says “Are you sure?”, identical oversized headings everywhere, fake social proof and text-only fake demos. The icon styles listed in file 13 are **vocabulary only**, never a mandate to add decorative icons. Keep existing anti-slop preferences intact.

## Established usability and psychology principles

| Principle | How it informs design |
| --- | --- |
| Aesthetic–Usability Effect | Perceived attractiveness can influence how usable an interface feels; do not confuse appearance with actual usability. |
| Hick’s Law | Limit unnecessary choices and organize complex decisions. |
| Fitts’s Law | Make important interactive targets appropriately sized and reachable. |
| Jakob’s Law | Respect familiar interaction patterns when appropriate. |
| Miller’s Law | Account for limits of short-term memory; avoid treating a fixed number as a universal rule. |
| Doherty Threshold | Timely system responses and feedback sustain interaction flow. |
| Law of Proximity | Group elements spatially when they belong together. |
| Law of Similarity | Make related objects visually consistent. |
| Law of Common Region | Use containers or boundaries where they clarify grouping. |
| Visual hierarchy | Differentiate information according to importance. |
| Progressive disclosure | Reveal complexity as needed rather than everything at once. |
| Recognition over recall | Keep options and context visible where practical. |
| Von Restorff Effect | Distinctive elements attract attention; reserve emphasis for meaningful priorities. |
| Peak–End Rule | Consider memorable moments and the ending of an experience. |
| Goal-Gradient Effect | Support motivation through clear, authentic progress toward goals. |
| Serial Position Effect | Recognize primacy/recency when ordering information. |
| Tesler’s Law | Manage inherent complexity rather than hiding it in confusing interactions. |
| Postel’s Law | Consider robustness of inputs/outputs while preserving validation and security. |
| Occam’s Razor | Prefer the simpler adequate explanation or design; avoid unnecessary additions. |
| Feedback loops | Show useful system responses to actions and states. |

## Avoid-by-default design patterns

| Area | Avoid | Interpretation |
| --- | --- | --- |
| Colors / effects | Purple gradients; harsh gradients; purple-and-black and purple-and-plastic defaults; rainbow coloring; generic neon colors and glows; generic basic pastel palettes | Avoid cliché color systems unless intentionally selected. |
| Colors / effects | White backgrounds as a universal default; low-contrast light-gray text on white | Choose background and text contrast for the product; never sacrifice readability. |
| Colors / effects | Liquid glass everywhere; generic glass cards; gratuitous radial orbs; dark grid-line backdrops; unnecessary dot grids | Do not let fashionable treatments substitute for information architecture. |
| Colors / effects | Drop shadows everywhere; the same corner radius and shadow on everything; generic soft corners | Use distinct treatment only when justified by hierarchy and function. |
| Colors / effects | Colored stripes in/around cards; unnecessary borders and outlines; decorative texture used merely as an accent | Decoration needs a purpose. |
| Typography / copy | All-caps eyebrow labels above every heading; oversized hero text; long noun-heavy headings | Avoid repetitive heading formulas. |
| Typography / copy | Space Grotesk as the automatic font; em dashes in website copy by default | Avoid default AI design/copy tropes; context may justify exceptions. |
| Typography / copy | “It’s not X, it’s Y” copywriting and other formulaic contrast phrases | Use direct, specific product language. |
| Icons / images | Lucide icons on every single screen; emoji icons; emojis in every heading; sparkle icons | Avoid generic ubiquitous visual symbols. |
| Icons / images | Emojis/icons as substitutes for real avatars, logos, or product images; synthetic/AI-slop stock photos | Do not replace authentic visuals with placeholders and claim they are real. |
| Cards / layouts | Three feature cards in a row by default; three pricing tiers by default; repetitive bento grids | Use only layouts and tier structures warranted by actual content. |
| Cards / layouts | Terminal windows as decoration; remote laptop mockups/screens; text pretending to be a product demo | Show authentic product behavior or avoid faux demonstrations. |
| Cards / layouts | Overstuffed screens; too much stuff; every section looking completely different | Create coherent structure without clutter or sameness. |
| Cards / layouts | Visual metaphors that need excessive explanatory labels; meaningless badges, dots, and status indicators | Decorative metaphors and indicators must communicate something verifiable. |
| Animation | Animated arrows; decorative hover animations; excessive scroll animations; cursor effects; heavy hero animations | Motion should clarify states/relationships, not simply move. |
| Animation | Motion “with nothing to say”; pointless animation in every section | Prefer meaningful feedback over spectacle. |
| Credibility | Proof that nobody can check; fake customer counters, fake statistics, fake testimonials, fake awards | No fabricated social proof. |
| Experience | No real product demos; desktop-only design; lack of mobile support | Test actual functionality and smaller screens. |
| Accessibility | Tiny text, insufficient contrast, hover-only essentials, obstructive fixed elements | Do not damage usability to achieve an aesthetic. |
| Unclear source notes | “borders around the clock”, “AX texture the accent”, “class guides”, “quick turn”, “random laptop colorings”, “colored left stride”, “when two kids stabbed in the window” | Retained verbatim as unconfirmed transcription; do not transform into automatic rules. |

## Useful interface features to consider / employ

| Feature | Applicability and guardrail |
| --- | --- |
| Dark mode / dark-mode toggle | If useful; make themes accessible and consistent. Do not require a dark mode on all sites. |
| Simple cookie banner | Only when applicable to tracking and local privacy requirements; avoid deceptive or unnecessary banners. |
| Site search | If the site has meaningful searchable content. |
| Back-to-top button | If page length and navigation justify it; avoid obstructing content. |
| Mobile menu | Where navigation requires it; test smaller screens and keyboard use. |
| Loading states / lightweight loading animations | Show real pending work; avoid fake or overlong animations. |
| Hover states | Provide interactive feedback, with touch/keyboard alternatives. |
| Footer bar / scroll-progress indicator | Consider only where meaningful; original phrase “food bar progress” uncertain. |
| Copy button | Where users need to copy data; provide success or failure feedback. |
| Print stylesheets | For useful printable pages, documents, and reports. |
| Sticky header | If it improves navigation; prevent it from hiding content. |
| Skip-to-content link | Use on pages with repeated navigation, enabling keyboard navigation. |
| Password visibility toggle | When password fields exist. |
| Form success state | Confirm actual submission success, not a fake acknowledgment. |
| Form error state | Explain failed submissions in accessible, actionable language. |
| Confirmation modals | For destructive or high-impact actions, not every simple click. |
| Last-updated date | Where content freshness matters; reflect an actual update. |
| Expandable FAQ | When useful for browsing; do not hide essential information. |
| Floating contact button | Where support access matters; avoid overlaps or obstruction. |
| Empty states | Explain what is missing and what action is possible. |
| Clear error messages | Explain what failed and recovery choices without exposing secrets. |
| Form validation feedback | Contextual validation with server-side validation for trust boundaries. |
| Responsive mobile layout | Design and test for mobile, not just desktop. |
| Custom 404 page | Offer navigation or recovery rather than a dead end. |
| Onboarding flow | Only if the application needs it; minimize unnecessary steps. |

## Theme-to-design-system transfer idea

Original notes: “Take the thing that you like, just go and purchase it,” then ask an agent (e.g. Argon) to make a “design FD file” so the theme can be transferred into other apps.

- Treat **“design FD file”** as **unresolved transcript terminology**, not a verified format.
- Capture the theme's layout, typography, spacing, colors, interactions, and reusable components as a reusable design specification if authorized by the theme's license.
- Do not assume purchasing a theme grants unlimited redistribution, cross-app reuse, or sublicensing rights. Respect the specific license.
